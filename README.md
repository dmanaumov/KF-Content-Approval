# КФ — Согласование задач (клиентский портал поверх Mattermost Boards)

Клиентский веб-кабинет для согласования материалов/задач. Никакой своей базы
данных — источник правды один: **Mattermost Boards**. Приложение на лету
читает карточки нужного борда через REST API и пишет статус согласования
обратно в ту же карточку.

## Как это устроено (коротко)

Реальный борд агентства («Задачи SMM-Team») — **один общий борд на всех
клиентов**, задачи разных клиентов различаются select-свойством `Проект`.
Поэтому:

- У каждого клиента — одна постоянная ссылка вида:
  `https://approve.example.com/p/{BOARD_ID}?project=Julias%20Interior&name=Julia%20Interiors&color=%2307605C`
  где `BOARD_ID` — ID борда (один и тот же для всех клиентов), а `project` —
  значение свойства «Проект» (label или, лучше, id опции), которое отличает
  задачи именно этого клиента. Ссылку один раз собирает сотрудник агентства
  и отправляет клиенту.
- Ссылка на конкретную карточку — тот же адрес плюс `&task={CARD_ID}`.
- Открывая ссылку, браузер клиента идёт в наш backend →
  `GET /api/boards/{boardId}/tasks?project=...` → backend опрашивает
  Mattermost Boards API, фильтрует карточки по «Проект» и возвращает только
  задачи этого клиента.
- Клиент жмёт «Согласовать» / «Есть правки» → backend тут же вызывает
  Mattermost API и меняет свойство карточки `Статус` (+ добавляет комментарий
  с текстом правок). Никакого промежуточного состояния, кроме короткого
  in-memory кэша на чтение (см. `CACHE_TTL_MS`).

**Важный нюанс, о котором стоит знать:** поле `Согласование`/`Статус`
переиспользует существующее внутреннее свойство `Статус` (так решили в
агентстве, чтобы не плодить второе свойство) — значит, когда клиент жмёт
«Согласовать»/«Есть правки», это **перезатирает** внутреннюю
production-стадию карточки (была «ТЗ РАЙТЕРУ» — станет «Согласовано НА
ПУБЛИКАЦИЮ» и т.п.). Карточки, у которых `Статус` ещё не дошёл до
клиентской стадии («Не начато», «В процессе», «ТЗ РАЙТЕРУ» и т.п.), в
кабинете клиента вообще не показываются — не считаются «ожидающими».

**Про безопасность:** так как борд общий, `project` в ссылке — это
единственное, что отделяет одного клиента от другого. Это НЕ
криптографический секрет — если его легко угадать (например, это просто имя
компании), теоретически можно подобрать значение и увидеть чужие задачи.
Для внутреннего use внутри агентства это может быть приемлемо, но если
ссылки уходят внешним клиентам — стоит обсудить более строгую защиту
(например, подписанный токен вместо label клиента). В текущей версии этого
нет сознательно, чтобы не усложнять раньше времени — но это стоит держать в
уме.

## Требования к борду в Mattermost

На борде должно быть настроено:

- Card-свойство `Проект` (или другое имя — `MM_PROJECT_PROPERTY_NAME`) типа
  **Select**, с опцией на каждого клиента.
- Card-свойство `Статус` (или другое — `MM_APPROVAL_PROPERTY_NAME`) типа
  **Select**, где среди опций есть:
  - `На согласование` — задача ждёт решения клиента;
  - опция для «согласовано» — сейчас `Согласовано НА ПУБЛИКАЦИЮ`;
  - опция для «есть правки» — сейчас переиспользуется существующая
    `Корректировка` (отдельную под клиентские правки не заводили);
  - `АРХИВ` — такие карточки скрываются из клиентского кабинета.

  Точные названия опций задаются через `MM_STATUS_*_LABEL` в `.env` и
  должны совпадать с реальными буква в букву (регистр важен).

  Любой другой `Статус` (внутренние стадии производства) клиенту просто не
  показывается — это ожидаемое поведение, не баг.

  **Важно про `Корректировка`:** раз отдельную опцию под клиентские правки не
  завели, а переиспользовали существующую — если сотрудник поставит карточке
  `Корректировка` по внутренней причине, никак не связанной с клиентом, эта
  карточка всё равно попадёт в кабинет клиента с пометкой «Правки» (мы не
  умеем отличить «клиент попросил правки» от «сотрудник сам решил
  скорректировать»). Если это окажется проблемой на практике — самое простое
  решение: завести отдельную опцию именно под клиентские правки.

Опционально: свойство-дата (`MM_PUBLISH_DATE_PROPERTY_NAME`) и
формат (`MM_FORMAT_PROPERTY_NAME`) — если оставить пустыми в `.env`, эти
поля просто не будут показаны в интерфейсе.

## Настройка

1. Скопировать `.env.example` → `.env`, заполнить:
   - `MATTERMOST_URL` — адрес вашего сервера Mattermost.
   - Авторизация — **два варианта, выбрать один**:
     - `MATTERMOST_LOGIN_ID` + `MATTERMOST_PASSWORD` — логин/пароль
       отдельного технического аккаунта (как в самой Boards UI). Это тот
       способ, который реально работает для ВСЕХ запросов на сервере
       агентства — их собственная n8n-интеграция использует именно его,
       Personal Access Token там не заработал вообще. **Рекомендуется для
       этого сервера.**
     - `MATTERMOST_TOKEN` — Personal Access Token отдельного технического
       аккаунта (бота). Подтверждённо работает для чтения (список
       досок/карточек) на сервере агентства, но не проверен для записи
       (согласование/правки от клиента) — если после «Согласовать» в
       интерфейсе ничего не меняется в Boards, или в логах видно `401`/`403`,
       переключитесь на логин/пароль выше.
     - Если заполнены оба — используется логин/пароль, `MATTERMOST_TOKEN`
       игнорируется.
   - `MATTERMOST_BOARDS_API_PREFIX` — см. `docs/MATTERMOST_INTEGRATION.md`,
     это отличается в зависимости от версии/деплоя Mattermost и **это надо
     проверить руками перед продакшеном**.
2. `docker compose up --build`
3. Контейнер слушает `:3000` и **не биндит** этот порт на хосте
   (`docker-compose.yml` использует `expose`, не `ports`) — наружу его
   пробрасывает сама платформа деплоя.

### Деплой через Dokploy (или Coolify и т.п.)

Такие платформы держат свой собственный reverse proxy (обычно Traefik) и
сами прокидывают домен на нужный порт контейнера — им не нужно, чтобы
docker-compose ещё и биндил порт на хосте самостоятельно. Поэтому в
`docker-compose.yml` порт объявлен через `expose`, а не `ports`.

В настройках приложения в Dokploy укажите:
- **Container Port**: `3000` (или значение вашего `PORT`, если поменяли);
- домен/поддомен, на который должен проксироваться этот порт.

Если раньше ловили `Bind for 0.0.0.0:3000 failed: port is already
allocated` — это было как раз из-за лишнего `ports: "3000:3000"` в
compose-файле, конфликтовавшего с портом, который уже занимала сама
платформа/другое приложение. С `expose` вместо `ports` такого конфликта
быть не должно.

### Деплой без платформы (голый `docker compose` на сервере)

Если поднимаете без Dokploy/Coolify и вам всё же нужен внешний доступ по
порту напрямую — добавьте в `docker-compose.yml` секцию `ports` руками,
например:

```yaml
    ports:
      - "3010:${PORT:-3000}"
```

и настройте свой nginx/reverse proxy на этот порт.

## Локальный запуск без Docker

```bash
cd backend
npm install
MATTERMOST_URL=... MATTERMOST_TOKEN=... npm start
```

## Параметры ссылки клиента

| Параметр | Обязателен | Назначение |
|---|---|---|
| путь `/p/{boardId}` | да | ID борда Mattermost |
| `project` | да, если у борда есть свойство «Проект» | Значение свойства «Проект» для этого клиента — id опции (надёжнее) или её текст. Без него на общем борде API откажет с `project_filter_required`, чтобы не показать чужие задачи |
| `task` | нет | ID карточки — открытая ссылка проскроллит и подсветит именно её |
| `name` | нет | Имя клиента в шапке (иначе покажется заглушка) |
| `color` | нет | Брендовый цвет клиента, HEX вида `%2307605C` |
| `logo` | нет | URL логотипа клиента |

Всё это просто параметры ссылки — хранить их отдельно не нужно, ссылку с
нужными параметрами один раз собирает сотрудник агентства при подключении
клиента.

## Важные ограничения этой версии

- **API Mattermost Boards официально не документирован** (подтверждено на
  форуме Mattermost). Реализация в `backend/src/mattermostClient.js`
  основана на чтении исходников плагина, а не на официальной спецификации.
  Перед продакшен-запуском обязательно пройти чек-лист в
  `docs/MATTERMOST_INTEGRATION.md`.
- Своей БД нет намеренно — при рестарте контейнера ничего не «теряется»,
  потому что состояние живёт в Mattermost. Единственный кэш — in-memory на
  чтение (`CACHE_TTL_MS`, по умолчанию 10 сек), обнуляется сразу после
  согласования/правок.
- Доступ к кабинету клиента защищён только тем, что ID борда трудно
  угадать — это не криптографический токен. Если нужен более строгий
  контроль доступа, самый простой вариант — добавить проверку статичного
  секрета в query (`&key=...`) на уровне nginx/reverse proxy перед этим
  сервисом; в код это сознательно не добавлено, чтобы не плодить сущности
  без необходимости.

## Структура проекта

```
backend/          Node.js/Express сервис (без БД)
  src/
    index.js            HTTP-роуты + in-memory кэш
    mattermostClient.js  Всё, что бьёт в Mattermost Boards API
    taskMapper.js         Сырые блоки Mattermost → нормализованная задача
    config.js              Вся конфигурация из ENV
frontend/         Статический клиентский кабинет (без сборки, чистый JS)
docs/
  MATTERMOST_INTEGRATION.md   Что именно проверить на реальном сервере
```
