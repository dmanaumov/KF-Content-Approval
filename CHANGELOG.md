# Changelog

Релиз-ноты KF Content Approval. Каждая запись — что изменилось и зачем; ведётся прямо в репозитории, чтобы не копировать текст туда-сюда отдельно.

## 2026-10-15 — Критичный баг: /team иногда не видел реально существующие задачи (DNS-коллизия алиаса 'db')

Несколько часов ловили пропадающие/404 карточки в /team при живых данных в базе — прямой SELECT COUNT(*) к Postgres САМ флип-флопил между 0 и 971 строкой на соседних запросах, без единого редеплоя или рестарта между ними. Проверили и отбросили: гонку TRUNCATE, рассинхрон boardId, два параллельных контейнера приложения (docker ps — всегда один), протухший кэш сборки, протухание пула соединений в процессе (рестарт app не лечил — значит, дело не в процессе).

Корень — на уровне Docker-сети, не кода: `docker-compose.yml` объявлял алиас `db` для сервиса Postgres на ОБЩЕЙ, `external: true` сети `dokploy-network`, которую на этом Dokploy-хосте делят ~8 разных проектов (my-kf, perf-kf, smm-saas, realty, pr-tool, typebot и др.) — судя по всему, склонированных с одного шаблона, где каждый тоже называет свою Postgres-службу `db` на той же общей сети. Встроенный Docker DNS при коллизии алиасов на одной сети отдаёт round-robin между ВСЕМИ контейнерами, претендующими на имя — подтверждено напрямую: `getent hosts db` из контейнера приложения возвращал то один IP, то другой на соседних вызовах. Приложение иногда коннектилось буквально к чужой базе другого проекта (и получало 0 строк без ошибки, так как POSTGRES_USER/POSTGRES_DB по умолчанию совпадали).

Исправлено на уровне инфраструктуры: `db`-сервис теперь занимает уникальный алиас `smm-tool-yg4ifn-pg` на `dokploy-network` вместо общего `db` (внутри default-сети самого compose-проекта имя `db` работает как и раньше — там коллизии нет, сеть изолирована per-проект). Строка подключения приложения (`DATABASE_URL`) обновлена на этот же уникальный адрес. Заодно, по просьбе пользователя — на будущий перенос Postgres в отдельную сущность — `DATABASE_URL` теперь можно целиком переопределить через `.env`/Dokploy Environment (`DATABASE_URL=postgres://...`); если не задан, собирается как раньше из `POSTGRES_*` плюс новый алиас.

Если n8n (см. `docs/N8N_AUTOMATION.md`) подключен к Postgres через Host `db` на этой же сети — нужно вручную поменять на `smm-tool-yg4ifn-pg`, иначе его подключение тоже попадёт под ту же DNS-коллизию (сам алиас `db` остаётся занятым другими проектами, просто этот проект на него больше не претендует).

Временная диагностика (`[team-tasks ...]`, `[team-card-404]` — независимый raw SELECT в обход pgTasks.js, логируется в `GET /api/team/tasks`, `GET /api/team/tasks/:taskId`, `requireTeamCardAccess`), добавленная в процессе поиска причины, оставлена в коде — безопасна (только логи), пригодится, если что-то похожее повторится.

## 2026-10-15 — Плашка "технические работы" в клиентском кабинете на время переноса

По прямому запросу пользователя: пока на борде идёт перенос с Mattermost или фоновая докатка медиа, клиенты (app.js, кабинет по ротируемой ссылке) могли видеть неполные/пропавшие карточки без объяснения. `GET /api/boards/:boardId/tasks` теперь отдаёт `migrationInProgress` (true, если `runState.state==='running'` ИЛИ `retryState.state==='running'` — см. mattermostMigration.js), `loadTasks()` в app.js показывает по этому флагу баннер над списком: «Идут технические работы — данные могут быть неполными. Уже совсем скоро закончим — простите за неудобство!». Автоматически скрывается, как только оба процесса завершены — никаких ручных действий. Версии `app.css`/`app.js` в index.html подняты (v23/v28), чтобы уже открытые у клиентов вкладки подхватили правку сразу, а не из кеша.

## 2026-10-15 — Статус переноса переживает рестарт контейнера (migration_run_report в Postgres)

Найдена и устранена причина сегодняшних повторяющихся «пропаж» баннера миграции в /team и цветной подсветки проектов в /projects: `runState.report` в `mattermostMigration.js` жил только в памяти процесса, а Dokploy на каждом деплое полностью пересоздаёт контейнер (`Recreate`), что эту память стирает. Раньше после рестарта `report` сам восстанавливался при следующем полном переносе — но после сегодняшней блокировки повторного запуска (`MIGRATION_RUN_LOCKED`) восстанавливаться ему стало неоткуда, и баннер/подсветка отключались НАВСЕГДА после первого же деплоя.

Исправлено: новая таблица `migration_run_report` (board_id → report jsonb) в Postgres. `persistReport(boardId)` сохраняет туда текущий `runState.report` при каждом релевантном изменении (конец полного переноса, конец/ошибка докатки медиа — оба места: автодокатка после переноса и ручная кнопка «Докатить медиа»). `hydrateRunStateFromDb(boardId)` читает его один раз при старте процесса (вызывается из стартовой последовательности в `index.js`, сразу после `waitForDb()`) и восстанавливает `runState.report`, если он ещё пуст — после этого `/api/team/migration-status` и блок подсветки в `GET /api/projects` снова видят `report` и показывают баннер/цвет как обычно, без ручных действий.

Важно: уже запущенная докатка медиа (стартовавшая до этого деплоя) этим фиксом не покрывается — её прогресс всё ещё в памяти старого процесса и при деплое оборвётся как раньше (без потери уже докаченных файлов, см. предыдущую запись — докатка идёт файл-по-файлу с немедленным коммитом в БД). После этого деплоя нужно будет просто нажать «Докатить медиа» ещё раз — дальше все рестарты переживаются сами.

ДОПОЛНЕНИЕ (тот же день, после первого деплоя этого фикса): выяснилось, что этого было недостаточно — persistReport() сохраняет уже СУЩЕСТВУЮЩИЙ report, а взяться ему было неоткуда: полный перенос (единственное место, где report раньше создавался) в этом процессе ни разу не выполнялся, и из-за MIGRATION_RUN_LOCKED больше не может. Докатка медиа (startMediaRetry) report не создавала, только дополняла его, если он уже был — то есть первый же деплой с этим фиксом молча ничего не чинил, даже пока докатка 46/371 шла полным ходом.

Исправлено по-настоящему: `computeMissingMediaTargets()` теперь также честно считает totalMattermostFiles (все Mattermost-медиа на борде, не только недокатанные). `startMediaRetry()` сам пересобирает минимальный report из этого счёта, если его ещё нет. А `hydrateRunStateFromDb()` на старте процесса, если в Postgres тоже пусто, не ждёт, пока кто-то нажмёт кнопку — сама делает один живой поход в Mattermost+Postgres и сохраняет честный report сразу при запуске контейнера. Теперь баннер в /team и подсветка на /projects появляются сами после ЛЮБОГО рестарта, без ручных действий.

## 2026-10-15 — Блокировка повторного переноса + докатка независимая от рестартов + честный статус проверки на уровне проекта

### Исправлено
- **Критическое**: «Докатить медиа» зависела от `report.mediaErrors` в памяти процесса — любой рестарт бэкенда (в т.ч. обычный передеплой) обнулял её, и кнопка залипала недоступной навсегда, потому что единственный способ пересобрать `report` («Выполнить перенос») теперь заблокирован (см. ниже). Новая `computeMissingMediaTargets()` в `backend/src/mattermostMigration.js` вместо этого сверяет ЖИВОЙ Mattermost с тем, что реально уже лежит в Postgres (`app_task_media.url`, по маркеру `mm_<id>` в имени файла, который проставляет `reuploadMattermostFile`) — работает в любой момент, независимо от того, что было в памяти процесса. `startMediaRetry()` стал асинхронным, роут `/api/ceo/mattermost-migration/retry-media` — тоже. Новый `pgTasks.getExistingMediaUrlsByTask()`. Кнопка в интерфейсе больше не блокируется заранее — бэкенд сам скажет, если докатывать нечего.

### Добавлено
- **Блокировка «Выполнить перенос»** (`backend/src/index.js`, `MIGRATION_RUN_LOCKED = true`, 423 на бэке + задизейбленная кнопка с пояснением на фронте) — по запросу пользователя, основной перенос карточек завершён, фаза 3 задеплоена, Mattermost больше не источник правды: повторный `TRUNCATE`-перенос теперь разрушителен. Снимать флаг осознанно, не случайным кликом.
- **`/projects` (админка)**: карточка каждого проекта теперь тоже подсвечивается статусом проверки переноса (тот же `issues`/`media_pending`/`ok`/`unreviewed`, что в `/team`) — цветная рамка + текстовый бейдж + лог подтверждения («кто и когда подтвердил / оставил замечание») прямо на карточке, под строкой «Менеджер». Новое поле `migrationReview` в ответе `GET /api/projects`.
- **`'ok'` (зелёный) теперь ТОЛЬКО после явного подтверждения** «Всё норм» — раньше был дефолтом для любой задачи/проекта без проблем, что ложно читалось как «команда проверила». До подтверждения — `'unreviewed'` (на карточках задач в `/team` — без подсветки, на карточках проектов в `/projects` — отдельная заметная синяя подсветка, т.к. там это и есть цель страницы).
- **Двухшаговое подтверждение «Всё норм»** в `/team` (раскрывает «Подтверждаешь, что план публикаций по проекту «X» переехал корректно?» с отдельной кнопкой) — защита от случайного клика. Кто подтвердил и когда — уже писалось в БД (`project_migration_review.reviewed_by_name`/`updated_at`), теперь ещё и показывается в интерфейсе.

### Контекст инцидента 2026-10-15
Рабочий день показал фактическую хрупкость in-memory состояния `runState`/`retryState`: передеплой (`docker compose up -d --build`, пересоздаёт контейнер `app`, НЕ трогая `db`) обнулял их среди дня, из-за чего баннер в `/team` на несколько минут пропадал, а «Докатить медиа» зависала недоступной — данные в Postgres при этом не страдали ни разу (подтверждено логами `db`-контейнера: ни одного `TRUNCATE` после первого успешного переноса 2026-10-14). Отдельно подтверждена и устранена гонка: таблица `project_migration_review` одно время реально отсутствовала в БД (создание не успело отработать при предыдущем старте — тот же класс сбоя, что раньше был у `app_task_feedback`), из-за чего `/team` на ~14 минут ловил 500 на каждый `GET /api/team/tasks` — устранилось следующим рестартом бэкенда (`initSchema()` отработал начисто).

## 2026-10-15 — Честная подсветка "медиа ещё докатывается" в /team (баннер + карточки)

### Исправлено
- Баннер и подсветка карточек в `/team` смотрели только на `report.mediaErrors` — список, который заполняется ТОЛЬКО когда файл не докатался даже после всех 6 попыток (минуты после переноса). Сразу после нового быстрого переноса (см. запись ниже) `mediaErrors` пуст, пока фоновая докатка ещё идёт — баннер ложно писал "все медиафайлы на месте", а карточки ложно зеленели (`media_pending` не выставлялся), хотя медиа ещё реально докатывается.
- `backend/src/mattermostMigration.js`: новый счётчик `pendingMediaTaskCounts` (taskId → сколько медиафайлов этой задачи ещё не разрешено ни успехом, ни окончательным провалом в ТЕКУЩЕЙ докатке) — заполняется в `startBackfillJob`/`startMediaRetry` (`markPendingTasks`), уменьшается по каждому файлу в `runBackfill` (`resolvePendingTask`). Новый экспорт `getPendingMediaTaskIds()`.
- `backend/src/index.js`: `annotateMigrationStatus()` теперь считает задачу `media_pending`, если её taskId есть либо в `mediaErrors` (постоянный провал), либо в `getPendingMediaTaskIds()` (ещё в активной докатке) — карточка не зеленеет раньше времени.
- `frontend/team.js`: `loadMigrationStatus()` переключён с условия `missingCount > 0` на `retryRunning` (живой прогресс докатки по `retryProgress`, а не по `missingCount`, который в момент активной докатки может быть ещё 0) — когда докатка реально закончена, баннер прямо пишет «Миграция медиа из ММ завершена. Просьба проверить корректность.» (с уточнением количества не докатавшихся файлов, если такие остались), вместо тихого "все на месте".

## 2026-10-15 — Перенос карточек отделён от докатки медиа (быстрый перенос + фоновая докатка с эскалирующим ретраем)

### Изменено
- Решение пользователя по следам реального прогона (971 карточка, ~2-3 часа, потому что КАЖДЫЙ Mattermost-файл перезаливался на диск СИНХРОННО внутри одной транзакции, и 208/371 упали с `share API: 429`): `runMigration()` в `backend/src/mattermostMigration.js` теперь БЫСТРЫЙ — TRUNCATE + заливка карточек/переписки/уже-дисковых медиа одной транзакцией, без ожидания Mattermost-файлов. Mattermost-медиа теперь никогда не перезаливается внутри этой транзакции — вместо этого сразу после commit АВТОМАТИЧЕСКИ стартует фоновая докатка ВСЕХ Mattermost-файлов (не только упавших).
- Докатка — свой движок с 5 повторами на файл и эскалирующим бэкоффом (1/5/10/30/60с между попытками, `reuploadMattermostFileWithBackoff`) — отдельно от встроенного ретрая `diskUpload.js` (`fetchWithAuthRetry429`, 2 попытки, короткий фиксированный бэкофф), который остался нетронутым, т.к. общий с живыми роутами `/team` и `/api/automation` — не хотели растягивать обычную загрузку одного файла командой до ~1.5 минут в худшем случае ради миграционного сценария.
- Движок общий для автоматического запуска (сразу после быстрого переноса, targets уже разрешены из того же прохода) и ручной кнопки «Докатить медиа» (для того, что осталось в `report.mediaErrors` после всех попыток — например, после перезапуска сервера). `startRun()` теперь также не даёт стартовать новый перенос, пока докатка ещё идёт (гонка: TRUNCATE снёс бы задачи, для которых докатка ещё пишет медиа).
- `frontend/migration.js`: отчёт о переносе показывает `pendingMediaCount` («Докатка N файлов идёт в фоне»), прогресс докатки показывается автоматически сразу после переноса, без ручного клика по кнопке.

## 2026-10-15 — Докатка медиа после переноса с Mattermost (фоновая кнопка)

### Добавлено
- Кнопка «Докатить медиа» на `/ceo/migration` — после основного переноса (фаза 2) часть Mattermost-файлов не перезаливается на disk.kontentferma из-за рейт-лимита его Sharing API (HTTP 429 под сустained-нагрузкой долгого переноса, см. комментарий `fetchWithAuthRetry429` в `diskUpload.js`); раньше такие файлы требовали ручного разбора JSON-отчёта. Кнопка запускает фоновую докатку именно этих файлов (список берётся из `mediaErrors` отчёта последнего запуска переноса) с прогресс-баром и логом по каждому файлу (успех/ошибка) — тот же паттерн фона+поллинга статуса, что и у самого переноса (`startRun`/`getRunStatus`).
- `backend/src/mattermostMigration.js`: `startMediaRetry(boardId)`/`getMediaRetryStatus()` — для каждого файла из `mediaErrors` заново читает карточку с Mattermost (чтобы найти файл и его позицию среди медиа — та же логика `mediaOrder`, что и у основного переноса), повторяет скачивание+перезаливку (`reuploadMattermostFile`) и доливает успешно докатанный файл в `app_task_media` (`pgTasks.insertMedia`), не трогая остальные таблицы. Успешно докатанные файлы сразу убираются из `mediaErrors` отчёта переноса — повторный клик кнопки повторяет только то, что всё ещё не получилось, без риска задвоить уже исправленные строки.
- Новые роуты: `POST /api/ceo/mattermost-migration/retry-media`, `GET /api/ceo/mattermost-migration/retry-media/status`.

## 2026-10-14 — Перенос задач с Mattermost на Postgres: переподключение роутов (фаза 3)

### Изменено
- Все роуты `index.js`, читающие/пишущие карточки/медиа/переписку (клиентский кабинет, кабинет команды, автоматизация n8n, CEO-отчёты, .ics-календарь, Цербер-фидбек), переведены с Mattermost Boards на три таблицы Postgres (`app_tasks`/`app_task_media`/`app_task_feedback`), наполненные фазой 2 (миграционная кнопка в `/ceo/migration`). Новый модуль `backend/src/pgTasks.js` — Postgres-замена `taskMapper.buildTasks()` и мутирующих вызовов `mattermostClient.js`.
- Решение по архитектуре (подтверждено пользователем 2026-10-14): список проектов/клиентов и полный каталог статус-опций СОЗНАТЕЛЬНО остаются на Mattermost (`mm.getBoard()` — дешёвый, ~100-300мс schema-вызов), а не переезжают в отдельную Postgres-таблицу. Единственное, что по-настоящему мигрировало — это сами карточки/медиа/переписка (`listCards`/`listBlocks`, тяжёлые вызовы, которые и создавали проблему — OOM, исчерпание сессий Mattermost).
- `loadBoard()` теперь возвращает только схему борда (`{board}`), без `cards`/`blocks` — сознательно ломает (fail loudly) любой забытый при переносе вызов вида `const {board, cards, blocks} = await loadBoard(...)` сразу и явно, вместо того чтобы молча отдать пустой список задач.
- Заодно устранён ряд классов кода, нужных только из-за особенностей Mattermost Boards и больше не нужных на Postgres: гонка merge-properties при записи одного свойства карточки, разделение подписи карточки на текстовые дочерние блоки (`isPureDiskLinkBlock`/`saveDescriptionText`), повторное чтение карточки после записи "на всякий случай" (Postgres сразу consistent), двойная схема id у медиа (Mattermost-блок vs хэш disk-ссылки — теперь единый `bigserial id` в `app_task_media`), собственная таблица `task_media_order` (теперь `app_task_media.position` — единственный источник порядка).
- `/api/ceo/mattermost-migration/preview` и `/run` (сам инструмент переноса, фаза 2) и диагностический `DEBUG_MATTERMOST`-роут `/api/debug/boards/:boardId/find` — единственные оставшиеся потребители "тяжёлого" чтения Mattermost (`mm.getBoard`+`listCards`+`listBlocks` напрямую, не через `loadBoard()`), оба намеренно не тронуты.

### Известные ограничения
- Полный live-smoke-тест (создание/правки/удаление карточки, approve/feedback от клиента, n8n-автоматизация, CEO-отчёты) не прогонялся из этой сессии — нет доступа к живой БД отсюда. Нужно проверить руками после деплоя.
- `backend/src/mediaOrder.js` (старая таблица `task_media_order`) больше не вызывается ни из одного роута — модуль и require в `index.js` оставлены как мёртвый код, не удалены (на случай, если какие-то немигрированные задачи ещё на неё ссылаются); можно почистить отдельным шагом после подтверждения, что таблица больше не нужна.

## 2026-10-14 — Перенос задач с Mattermost на Postgres: схема + кнопка в CEO-интерфейсе

### Добавлено
- Схема в Postgres под будущее хранилище задач/медиа/переписки: `app_tasks`, `app_task_media`, `app_task_feedback` (замена Mattermost Boards как хранилища карточек — причины и план: `claude/kf-mattermost-to-postgres-migration.md` в проекте «Мои IT дела»).
- Новая вкладка CEO-панели «Миграция» (`/ceo/migration`): предпросмотр переноса (ничего не пишет, только считает) и отдельная кнопка реального запуска с подтверждением. Запуск идёт в фоне (не ждём его в HTTP-ответе — на ~1000+ карточках это минуты), прогресс и результат — через поллинг статуса.
- API: `GET /api/ceo/mattermost-migration/preview`, `POST /api/ceo/mattermost-migration/run`, `GET /api/ceo/mattermost-migration/status` (все — только для CEO).
- Перенос переиспользует текущую логику разбора карточек (`taskMapper.js`) и полностью перезаливает Mattermost-медиафайлы на disk.kontentferma (консолидация медиа в одном месте); переписка по согласованию переносится целиком, включая внутренние служебные пометки, а не только клиентский срез.
- Перенос идемпотентен: каждый запуск полностью пересобирает три таблицы заново (TRUNCATE + заливка) — повторный клик не задваивает данные.

### Известные ограничения
- Это пока только подготовка данных — роуты `index.js`, читающие/пишущие задачи, ещё работают через Mattermost как раньше (следующая фаза — переподключить их на эти таблицы). Нажатие «Выполнить перенос» заполняет Postgres, но приложение продолжает показывать данные из Mattermost, пока эта фаза не сделана.
- Частичная неудача перезаливки отдельного медиафайла не останавливает весь перенос — такой файл просто попадает в список ошибок в отчёте для ручного разбора.
