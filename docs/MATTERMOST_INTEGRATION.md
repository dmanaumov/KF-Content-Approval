# Интеграция с Mattermost Boards — что нужно проверить перед продакшеном

Boards API у Mattermost официально не документирован (это подтверждается и
на форуме самого Mattermost: "Boards endpoints aren't in the main API docs
yet"). Всё, что ниже реализовано в `backend/src/mattermostClient.js`,
восстановлено по исходникам плагина `mattermost-plugin-boards`
(регистрация роутов в `server/api/*.go`), а не по официальной спецификации.
Это рабочая отправная точка, а не гарантированно точный контракт для вашей
конкретной версии сервера.

## 1. Правильный префикс API — ПОДТВЕРЖДЁНО для сервера агентства

В `.env` есть `MATTERMOST_BOARDS_API_PREFIX`. Для сервера агентства
(`messager.kontentferma.com`) подтверждено вживую — через уже работающий
собственный n8n-воркфлоу агентства (реальные запросы, не документация), что
правильный префикс это:

- `/plugins/focalboard/api/v2` — плагин с id `focalboard` (теперь значение
  по умолчанию в этом проекте).

Другие варианты, которые встречаются в природе на *других* серверах, если
когда-нибудь понадобится переключить эту установку на другой Mattermost:

- `/plugins/boards/api/v2` — Mattermost 9+, Boards встроен как плагин с id `boards`.
- `/api/v2` — отдельно стоящий Focalboard personal server (не через Mattermost).

**Как проверить быстро на новом сервере:** открыть Boards в браузере под тем
же сервером, открыть DevTools → Network, обновить страницу борда — увидите
реальные запросы к API и их точный префикс. Ещё надёжнее — если у вас, как
и у агентства, уже есть рабочая интеграция (n8n/Zapier/скрипт), которая
дёргает Boards API — посмотреть точные URL там.

## 1а. Получение борда и карточек — ПОДТВЕРЖДЁННЫЕ эндпоинты

Изначально `getBoard()` дёргал `GET /boards/{boardId}` напрямую, а карточки
пытался получить через общий `GET /boards/{boardId}/blocks` — оба варианта
не сработали на реальном сервере агентства (второй отдавал `404 page not
found`, см. историю отладки). Взамен подтверждены вживую (тем же n8n-
воркфлоу агентства, который реально работает в проде) два эндпоинта:

```
GET {prefix}/teams/{teamId}/boards
GET {prefix}/boards/{boardId}/cards?page=0&per_page=200
```

Первый отдаёт массив бордов команды, каждый с полным `cardProperties` —
`getBoard(boardId, teamId)` получает этот список и ищет нужный борд в нём.
Из-за этого **`MATTERMOST_TEAM_ID` обязателен** — берётся из URL борда:
`.../boards/team/{teamId}/{boardId}/{viewId}/{cardId}`.

Второй — **основной источник карточек** (`mattermostClient.listCards()`),
свойства карточки лежат прямо в `card.properties[propertyId]` (не
`card.fields.properties`, как в общей модели Focalboard Block — это была
реальная ошибка, поймана и исправлена по данным с продакшена). Пагинация не
реализована сверх `per_page=200` — если у клиента когда-нибудь будет больше
200 карточек на борде одновременно, это надо будет доработать.

Общий `GET {prefix}/boards/{boardId}/blocks` (используется только в
`listBlocks()` для подписей/медиа/комментариев-карточек) остаётся
**неподтверждённым** на этом сервере — код трактует его как best-effort:
ошибка там не валит весь запрос списка задач, карточки просто показываются
без подписи/медиа/фидбека. См. пункты 4 и 5 ниже — PATCH и создание
комментария идут через тот же неподтверждённый `/blocks`-эндпоинт и тоже
требуют проверки на реальном сервере.

## 2. Аутентификация — два режима

Код поддерживает два способа (см. `mattermostClient.js`), оба в итоге шлют
`Authorization: Bearer <token>` + `X-Requested-With: XMLHttpRequest` на
Boards API (второй заголовок — по исходникам плагина роут `requireCSRFToken`
ожидает его для сессионной cookie-авторизации; для PAT вроде не обязателен,
но отправляется всегда на всякий случай):

**Режим A — логин/пароль (`MATTERMOST_LOGIN_ID` + `MATTERMOST_PASSWORD`),
рекомендован для сервера агентства.** Причина: у агентства уже есть
собственная рабочая n8n-интеграция с этим же сервером, и там **PAT не
заработал вообще** — используется `POST /api/v4/users/login` с
`{login_id, password}`, а дальше token из ответа. По присланному примеру
ноды n8n токен там достают из cookie `MMAUTHTOKEN` (нода называется "Extract
Cookies"), а не только из заголовка `Token` ответа. Наш `login()` пробует
оба источника — сначала заголовок `Token`, если его нет — парсит
`Set-Cookie: MMAUTHTOKEN=...`. Токен кэшируется в памяти процесса (не в БД),
при `401` от любого запроса — автоматический повторный логин и одна
повторная попытка.

**Режим B — Personal Access Token (`MATTERMOST_TOKEN`).** Подтверждённо
работает для GET-запросов этого приложения против реального сервера (видно
в продакшен-логах — `listTeamBoards`/`listCards` возвращают настоящие
данные). Не проверялся для PATCH/POST (согласование/правки) — если после
«Согласовать» статус не меняется, или в логах `401`/`403`, переключайтесь на
режим A.

Если заполнены оба варианта в `.env` — используется режим A, `MATTERMOST_TOKEN`
игнорируется целиком.

Проверить: включить `DEBUG_MATTERMOST=true`, запустить `GET
/api/boards/{boardId}/tasks` и посмотреть в логах контейнера, приходит ли
осмысленный ответ, а не 401/403. При режиме A в логах будет строка
`login() → session token acquired (source: ...)`.

## 3. Формат свойства-даты

Значения date-свойств у Focalboard в разных версиях наблюдались в разных
видах: JSON-строка `{"from":1692400000000}`, «голый» epoch в миллисекундах,
простая строка `YYYY-MM-DD`. `taskMapper.js` (`parsePropertyDate`) пробует
все три варианта по очереди и возвращает `null`, если не подошёл ни один —
в этом случае дата публикации в интерфейсе просто не покажется, ничего не
упадёт. Если у вас на сервере другой формат — здесь единственное место,
которое нужно доработать.

## 4. Payload для PATCH свойства карточки

`patchCardProperty()` отправляет:

```json
PATCH /boards/{boardId}/blocks/{blockId}
{ "updatedProperties": { "<propertyId>": "<optionId>" } }
```

Это соответствует структуре `model.BlockPatch` из исходников Focalboard
(`UpdatedProperties map[string]string`).

**Подтверждена реальная проблема на сервере агентства**: PATCH возвращал
`200 OK`, но статус карточки в самой Mattermost Boards не менялся —
приложение при этом показывало клиенту «Согласовано», хотя по факту ничего
не согласовалось. Из-за этого `setApprovalStatus()` в `index.js` теперь
**перепроверяет** результат: после PATCH перечитывает карточку и сравнивает
её реальный статус с ожидаемым. Если не совпало — бросает ошибку с понятным
текстом вместо того, чтобы врать об успехе. Если вы сейчас видите эту
ошибку в интерфейсе — значит PATCH формально проходит, но не применяется.
Вероятные причины (по убыванию вероятности):
1. Аккаунт, от имени которого идёт запрос (см. §2 — режим A/B), не имеет
   прав на редактирование именно этой карточки/борда (только чтение).
2. Формат `updatedProperties` всё-таки отличается на этой версии сервера.
3. `blockId` в пути должен быть не id карточки, а id какого-то другого блока.

Первым делом проверить пункт 1 — включить `DEBUG_MATTERMOST=true`, в логах
будет строка `patchCardProperty(...) response →` с сырым ответом сервера.

## 5. Payload для комментария (правки)

`addCardComment()` создаёт блок типа `comment` через:

```json
POST /boards/{boardId}/blocks
[{ "id": "...", "boardId": "...", "parentId": "<cardId>", "type": "comment", "title": "<текст>", ... }]
```

Тоже best-effort реконструкция по модели блоков Focalboard. Если комментарии
не появляются на карточке в Mattermost — второе место для проверки тем же
способом (DevTools Network на реальном добавлении комментария руками).

## 6. Файлы/медиа

Файлы, прикреплённые к карточке, отдаются через **основной** (стабильный,
официально документированный) файловый API Mattermost:
`GET /api/v4/files/{fileId}` с тем же Bearer-токеном. Он не публичный, поэтому
наш backend проксирует байты через `/api/files/{fileId}` — включая
пересылку заголовка `Range`, это важно для воспроизведения видео на iPhone
Safari (проверялось на моках, `206 Partial Content` пробрасывается корректно
— но финальная проверка на реальном видео с реального сервера обязательна).

## 7. Общий борд на всех клиентов (реальная схема агентства)

Борд «Задачи SMM-Team» — один на всех клиентов, разделение по клиентам идёт
через select-свойство `Проект`. Это значит:

- `MM_PROJECT_PROPERTY_NAME` обязателен к настройке (по умолчанию `Проект`).
- Ссылка клиента ОБЯЗАНА содержать `?project=...` — иначе `/api/boards/.../tasks`
  вернёт `400 project_filter_required`, а не список задач (специально, чтобы
  не показать чужие карточки).
- `project` можно передавать как id опции свойства «Проект» (надёжнее,
  стабильнее к переименованиям) или как точный текст label — сопоставление
  регистронезависимое, но лучше использовать id.
- `Статус` (свойство согласования) — существующее внутреннее свойство
  агентства, переиспользуется как есть, а не заводится отдельное. Из-за
  этого approve/feedback от клиента **перезаписывают** внутреннюю
  production-стадию карточки — это осознанный выбор агентства, не баг кода.
- Опция «правки» (`MM_STATUS_CHANGES_LABEL`) сейчас = существующая
  `Корректировка`, отдельную под клиентские правки не заводили — то есть
  внутренняя пометка «нужна корректировка» и «клиент попросил правки»
  неразличимы для этого приложения.

## Чек-лист перед продакшеном

- [x] `MATTERMOST_BOARDS_API_PREFIX` — подтверждён (`/plugins/focalboard/api/v2`)
      для сервера агентства. Если разворачиваете на другом сервере Mattermost —
      перепроверить по п.1.
- [ ] `MATTERMOST_TEAM_ID` заполнен (из URL борда).
- [ ] Выбран и заполнен один из режимов авторизации (см. п.2) —
      `MATTERMOST_LOGIN_ID`+`MATTERMOST_PASSWORD` (рекомендовано для этого
      сервера) либо `MATTERMOST_TOKEN`; в логах видно, что список бордов и
      карточек реально приходит, а не `401`/`403`.
- [ ] На борде есть свойство «Проект» с опцией на каждого клиента —
      `MM_PROJECT_PROPERTY_NAME` совпадает буква в букву.
- [ ] Ссылки клиентов содержат правильный `?project=`, задачи одного клиента
      не показывают карточки другого (проверить руками с двумя разными
      значениями `project`).
- [ ] `MM_STATUS_*_LABEL` совпадают буква в букву с реальными опциями
      свойства `Статус`.
- [ ] «Согласовать» в интерфейсе реально меняет `Статус` карточки в Boards UI.
- [ ] «Есть правки» реально добавляет комментарий и меняет `Статус` на
      `Корректировка` в Boards UI.
- [ ] Видео с реального борда проигрывается на iPhone Safari (Range/206).
- [ ] Карточки с `АРХИВ` и с внутренними стадиями (`Не начато`, `В процессе`,
      `ТЗ РАЙТЕРУ` и т.п.) не показываются клиенту.
- [ ] Проверено поведение при недоступном Mattermost (учения: остановить
      Mattermost, убедиться что клиент видит понятную ошибку, а не белый экран).
