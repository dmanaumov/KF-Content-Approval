# Задача для разработчика n8n: автопубликация согласованных постов

## Статус этого документа

Это черновик технического задания, написанный на основе того, что уже есть
в проекте (кабинет согласования, Postgres со ссылками/лого/креды соцсетей).
**Дмитрию стоит просмотреть раздел «Что нужно подтвердить перед стартом»
внизу и поправить/убрать пункты, прежде чем передавать это разработчику
n8n** — там помечено, что взято прямо из вашей формулировки, а что я
предположил сам как разумный дефолт.

**Это НЕ единственная интеграция в этом документе.** Разделы 1-5 ниже —
публикация согласованного SMM-контента (`X-Api-Key`/`AUTOMATION_API_KEY`).
Отдельно, своим ключом (`X-Bot-Key`/`BOT_API_KEY`) — см. **раздел 6**:
Telegram-бот «Кот Василий», регистрация чатов и переписка с лидами.

### `GET /api/automation/projects/{projectId}/credentials` — подробно

**Параметры:**

| Параметр | Где | Обязателен | Значения | Описание |
|---|---|---|---|---|
| `projectId` | path | да | id опции свойства "Проект" | см. `GET /api/automation/projects` |
| `network` | query | нет | `ig` \| `tg` \| `vk` \| `ok` \| `max` | если передан — вернуть креды только этой сети |
| `X-Api-Key` | header | да | значение `AUTOMATION_API_KEY` | тот же ключ, что и для всех `/api/automation/*` |

**Без `network`** — весь набор сразу:
```
GET /api/automation/projects/ajdkoks6pmti4bk388yuarrjdnr/credentials
X-Api-Key: <ваш ключ>
```
```json
{
  "projectId": "ajdkoks6pmti4bk388yuarrjdnr",
  "credentials": {
    "ig": { "accessToken": "...", "igUserId": "..." },
    "tg": { "botToken": "...", "chatId": "..." }
  }
}
```
(в объекте `credentials` — только те сети, для которых что-то реально заполнено в попапе "Редактировать"; сеть без кредов просто отсутствует как ключ, это не ошибка).

**С `network`** — только одна сеть, отдаётся напрямую (без обёртки ещё раз под `ig`):
```
GET /api/automation/projects/ajdkoks6pmti4bk388yuarrjdnr/credentials?network=ig
X-Api-Key: <ваш ключ>
```
```json
{
  "projectId": "ajdkoks6pmti4bk388yuarrjdnr",
  "network": "ig",
  "credentials": { "accessToken": "...", "igUserId": "..." }
}
```
Если у этого проекта для запрошенной сети ничего не настроено (агентство ещё не заполнило попап) — `credentials` придёт `null` (HTTP 200, это ожидаемое состояние, не ошибка):
```json
{ "projectId": "ajdkoks6pmti4bk388yuarrjdnr", "network": "vk", "credentials": null }
```

**Ошибки**: `400 project_id_required` / `400 project_not_found` (плохой/неизвестный `projectId`), `400 invalid_network` (значение `network` не из списка `ig`/`tg`/`vk`/`ok`/`max`), `401` без корректного `X-Api-Key`.

**Рекомендация**: если ваш workflow уже определил сеть карточки на шаге 3 (`GET /api/automation/tasks` → `network` в каждой задаче), сразу передавайте `?network=<то самое значение>` — тогда каждый вызов несёт только один реально нужный секрет, а не все пять сетей проекта разом.

Авторизация — заголовок `X-Api-Key: <значение AUTOMATION_API_KEY>` (задаётся
в Dokploy, НЕ реальный логин/пароль Mattermost — см. комментарий в
`backend/src/config.js`). Без него все `/api/automation/*` отвечают 503, пока
переменная не задана.

**id статусов Mattermost («Согласовано», «На согласование» и т.д.) для этого
API больше не нужны вообще** — все проверки/переводы статуса делаются этим
приложением по тексту метки, так же как во всём остальном коде.

**Полная схема запросов/ответов — Swagger/OpenAPI**, доступен только владельцу
(CEO): `https://smm.kontentferma.com/swagger` (короткий алиас, НОВОЕ; старый
адрес `https://smm.kontentferma.com/ceo/api-docs` тоже продолжает работать —
это один и тот же экран) — нужно быть залогиненным в `/team` под аккаунтом из
`CEO_EMAILS`. Отдельно JSON-спека —
`GET /api/ceo/openapi.json` (тот же доступ) — её можно скачать и передать
разработчику n8n напрямую, n8n умеет импортировать OpenAPI-спеку и сам
собирает HTTP-ноды по ней.

Разделы 1–6 ниже остаются актуальными для ЧТЕНИЯ (Postgres project_settings)
и как справочный материал о внутреннем устройстве Mattermost Boards — но для
самой записи (создание карточки, медиа, отметка «Опубликовано») используйте
раздел 0 выше, он проверенный и safety-checked этим приложением, а не собран
вручную.

**Про `social_credentials` конкретно — теперь ДВА способа, выбирайте любой**:
1. **HTTP, `GET /api/automation/projects/{projectId}/credentials`** (см. раздел
   0 выше) — не нужна отдельная сессия/подключение к Postgres, только тот же
   `X-Api-Key`, что и для остального. Добавлено 2026-08-25 специально, чтобы
   весь цикл публикации (что публиковать → чем публиковать → отчитаться)
   шёл через один и тот же API.
2. **Прямой Postgres** (см. раздел 1 ниже, роль `n8n`) — по-прежнему работает,
   если у вас уже есть подключение к БД для `publication_log` и удобнее не
   делать лишний HTTP-вызов.

**Важно про безопасность именно этого пункта**: и HTTP-ключ (`X-Api-Key`), и
Postgres-пароль роли `n8n` дают доступ к настоящим секретам соцсетей клиентов
(что бы вы ни выбрали) — обращайтесь с ними как с любым другим реальным
credential (не коммитить в git, не логировать, ротировать при подозрении на
утечку).

### `POST /api/automation/projects/{projectId}/credentials` — подробно

Добавлено 2026-09-03 — write-половина к `GET`-эндпоинту выше, для авторефреша IG-токенов (Business-токены живут ~60 дней) и подключения новых аккаунтов без ручных правок в БД/попапе "Редактировать".

**Параметры:**

| Параметр | Где | Обязателен | Значения | Описание |
|---|---|---|---|---|
| `projectId` | path | да | id опции свойства "Проект" | см. `GET /api/automation/projects` |
| `X-Api-Key` | header | да | значение `AUTOMATION_API_KEY` | тот же ключ, что и для всех `/api/automation/*` |
| `network` | body | да | `ig` \| `tg` \| `vk` \| `ok` \| `max` | какую сеть обновляем |
| остальные поля | body | нет* | что угодно | сохраняются как есть — формат каждой сети на ваше усмотрение, как и раньше (см. п.3 в конце документа); *хотя бы одно поле кроме `network` обязательно |

```
POST /api/automation/projects/ajdkoks6pmti4bk388yuarrjdnr/credentials
X-Api-Key: <ваш ключ>
Content-Type: application/json

{
  "network": "ig",
  "accessToken": "EAAG...",
  "igUserId": "17841400000000000",
  "expiresAt": "2026-11-01T00:00:00Z"
}
```
Ответ (200) — итоговый объект кредов ЭТОЙ сети после слияния, зеркально single-network форме `GET`:
```json
{
  "projectId": "ajdkoks6pmti4bk388yuarrjdnr",
  "network": "ig",
  "credentials": {
    "accessToken": "EAAG...",
    "igUserId": "17841400000000000",
    "expiresAt": "2026-11-01T00:00:00Z",
    "lastRefreshedAt": "2026-09-03T12:00:00.000Z"
  }
}
```

**Это UPSERT с ЧАСТИЧНЫМ СЛИЯНИЕМ (shallow merge), не полная замена**: поля, которые вы НЕ прислали в этом вызове, остаются как были. Например, при рефреше можно прислать только:
```json
{ "network": "ig", "accessToken": "EAAG_НОВЫЙ...", "expiresAt": "2026-11-01T00:00:00Z" }
```
— `igUserId`, заполненный раньше, никуда не денется. Если нужно ПОЛНОСТЬЮ заменить объект сети (например убрать поле) — либо явно пришлите его пустой строкой/null внутри вашего же поля, либо используйте попап "Редактировать" на `/projects` для ручной зачистки.

**`lastRefreshedAt` проставляется сервером на КАЖДЫЙ вызов автоматически** — своё значение прислать нельзя, оно игнорируется/перезаписывается. Это ваш сигнал "когда это приложение последний раз реально записало сюда что-то", независимо от того, что вы прислали в `expiresAt`.

**`expiresAt` — не обязателен, но настоятельно рекомендуется**: без него этот креды не попадёт в выдачу `GET /api/automation/credentials` ниже (эндпоинт фильтрует именно по этому полю). Сеть без естественного истечения токена (например VK/OK с долгоживущим токеном) может его не присылать вовсе — тогда просто никогда не появится в списке "скоро истекает", что и логично.

**Ошибки**: `400 project_id_required` / `400 project_not_found`, `400 network_required` (поле `network` не передано), `400 invalid_network`, `400 fields_required` (в теле кроме `network` пусто), `400 invalid_expires_at` (значение `expiresAt` не парсится как дата — используйте ISO 8601), `401` без корректного `X-Api-Key`.

**Никогда не логируется** — как и `GET`-версия, даже при включённом `DEBUG_MATTERMOST` (см. `isCredentialsRoute` в `backend/src/index.js`).

### `GET /api/automation/credentials` — подробно

Добавлено 2026-09-03 вместе с `POST` выше — "у кого скоро протухнет токен", одним вызовом по всем проектам сразу, чтобы флоу авторефреша не гонял по 10+ проектам циклом (лишняя нагрузка, лишние точки отказа).

**Параметры:**

| Параметр | Где | Обязателен | Значения | Описание |
|---|---|---|---|---|
| `expiringWithinDays` | query | **да** | целое число 1–365 | окно в днях от текущего момента |
| `network` | query | нет | `ig` \| `tg` \| `vk` \| `ok` \| `max` | если не задан — по всем сетям сразу |
| `X-Api-Key` | header | да | значение `AUTOMATION_API_KEY` | тот же ключ |

```
GET /api/automation/credentials?network=ig&expiringWithinDays=7
X-Api-Key: <ваш ключ>
```
```json
{
  "credentials": [
    {
      "projectId": "ajdkoks6pmti4bk388yuarrjdnr",
      "projectLabel": "Контент Ферма",
      "network": "ig",
      "expiresAt": "2026-09-08T00:00:00Z",
      "lastRefreshedAt": "2026-07-10T09:15:00.000Z"
    }
  ]
}
```

**Результат ВКЛЮЧАЕТ уже истёкшие креды** (`expiresAt` в прошлом), не только те, что истекут в ближайшие `expiringWithinDays` дней — им внимание нужно как минимум не меньше, поэтому не нужен отдельный вызов для "уже сломанного".

**Намеренно НЕ содержит сам секрет** (`accessToken` и т.п.) — тот же принцип, что и у одно-проектного `GET` выше: один скомпрометированный ответ не должен раскрывать токены сразу всех клиентов разом. Рекомендуемый флоу авторефреша:
1. `GET /api/automation/credentials?network=ig&expiringWithinDays=7` — кого рефрешить.
2. Для каждого найденного `projectId`: `GET /api/automation/projects/{projectId}/credentials?network=ig` — забрать текущий (ещё живой) токен, чтобы обменять его на новый через API IG.
3. `POST /api/automation/projects/{projectId}/credentials` — записать новый `accessToken`/`expiresAt`.

Если вашему workflow действительно нужен сам секрет прямо в этой выдаче (например чтобы не делать шаг 2 отдельно) — это реальный компромисс безопасности, обсудите с Дмитрием перед тем как менять на своей стороне через прямой Postgres-доступ.

**Ошибки**: `400 invalid_expiring_within_days` (параметр не передан или вне диапазона 1–365), `400 invalid_network`, `401` без корректного `X-Api-Key`.

### Где именно живут тема, ключевые слова, текст поста и медиа — сводка

Это то, что чаще всего путают при интеграции, поэтому отдельно, одним местом:

| Что | Где | Метод чтения | Метод записи |
|---|---|---|---|
| **Тема / заголовок поста** | `card.title` в Mattermost (с необязательным префиксом сети `ig:`/`tg:`/...) | `title` в ответе `GET /api/automation/tasks` и `GET /api/automation/tasks/{taskId}` | только при создании — `title` в `POST /api/automation/tasks`. Изменить у существующей карточки через `/api/automation/*` сейчас нельзя (скажите, если нужен отдельный метод) |
| **Ключевые слова / мысли** | отдельное текстовое свойство карточки «Ключевые слова/мысли» — НЕ то же самое, что текст поста, для команды/агентства, клиенту не показывается | `keywords` в ответе `GET /api/automation/tasks` и `GET /api/automation/tasks/{taskId}` | `keywords` в `POST /api/automation/tasks` (при создании) или `POST /api/automation/tasks/{taskId}/keywords` (у существующей карточки) |
| **Текст поста (тело)** | НЕ свойство карточки, а её содержимое (text-блоки Mattermost, «описание» карточки) | `caption` в ответе `GET /api/automation/tasks` и `GET /api/automation/tasks/{taskId}` | `text` в `POST /api/automation/tasks` (при создании) или `POST /api/automation/tasks/{taskId}/text` (у существующей карточки) |
| **Медиа (фото/видео)** | вложения карточки + ссылки disk.kontentferma, в порядке, который выбрал клиент | `media[]` в ответе `GET /api/automation/tasks` и `GET /api/automation/tasks/{taskId}` (каждый объект — `{id, kind, source, shareUrl/imageUrl, name,...}`) | `media` (массив готовых ссылок) в `POST /api/automation/tasks` при создании; либо `POST .../media-link` \| `.../media-upload` \| `.../media-import` для существующей карточки (см. раздел 0 выше), порядок — `.../media-order` |
| **Чат с клиентом** (НЕ внутренние аудит-комментарии автоматизации) | переписка команда↔клиент, видна клиенту в его кабинете согласования | `clientComments[]` (`kind: 'approved' \| 'feedback' \| 'agency' \| 'correction'`) в ответе `GET /api/automation/tasks` и `GET /api/automation/tasks/{taskId}` | `POST /api/automation/tasks/{taskId}/client-message` — {text?, imageUrl?} |

**Важно не перепутать `keywords` и `caption` («текст поста»)** — это два разных поля с разным назначением: `keywords` — внутренний бриф/мысли для копирайтера, никогда не попадает к клиенту; `caption` — это и есть готовый текст поста, который в итоге публикуется в соцсеть.

«Редактировать» → вкладка «ИИ настройки» на `/projects`). Не включает

`X-Api-Key`.

### Создание и обновление карточки — сквозной пример

Тема поста, ключевые слова и текст задаются в РАЗНЫХ полях — сравните:

**1) Создать карточку** — тема (`title`), сеть (`network`), текст поста
(`text`), ключевые слова (`keywords`) и уже готовое медиа — всё одним
вызовом:
```
POST /api/automation/tasks
X-Api-Key: <ваш ключ>
Content-Type: application/json

{
  "title": "Летняя коллекция",
  "network": "ig",
  "projectId": "ajdkoks6pmti4bk388yuarrjdnr",
  "text": "Встречайте новую летнюю коллекцию! Скидка 20% до конца месяца.",
  "keywords": "пляж, отпуск, скидка 20%, акцент на молодую аудиторию",
  "publishDate": "2026-09-01",
  "media": ["https://disk.kontentferma.com/s/abc123"]
}
```
```json
{ "task": { "id": "bxyz1234567890abcdefghijk", "title": "ig: Летняя коллекция", "caption": "Встречайте новую летнюю коллекцию!...", "keywords": "пляж, отпуск, скидка 20%, акцент на молодую аудиторию", ... }, "bytesSaved": 71 }
```
(`network` сам допишется префиксом к `title` — на входе не нужно писать
`ig:` руками, а `GET`/список потом снова распознает сеть по этому же
префиксу).

**2) Обновить ТОЛЬКО текст поста** (тему и ключевые слова не трогает):
```
POST /api/automation/tasks/bxyz1234567890abcdefghijk/text
X-Api-Key: <ваш ключ>
Content-Type: application/json

{ "text": "Обновлённый текст: скидка теперь 25%!" }
```
```json
{ "task": { "id": "bxyz1234567890abcdefghijk", "caption": "Обновлённый текст: скидка теперь 25%!", ... }, "bytesSaved": 54 }
```
**`bytesSaved`** (НОВОЕ) — размер `caption` В БАЙТАХ (UTF-8, не количество символов — кириллица весит по 2 байта на букву), посчитанный ПОСЛЕ повторного чтения карточки из Mattermost, а не по тексту из запроса — то есть это подтверждение того, что реально сохранилось, а не эхо того, что вы отправили. Если хотите явно проверить, что ничего не потерялось/не обрезалось — сравните с `Buffer.byteLength(text, 'utf8')` (Node) на своей стороне: несовпадение значит, что сохранённый текст отличается от отправленного. Этот же `bytesSaved` добавлен и в ответ `POST /api/automation/tasks` (создание — тоже сохраняет текст поста), считается от `task.caption`.

**НАЙДЕН И ИСПРАВЛЕН реальный баг (2026-08-27): текст сохранялся, но не отображался в самом Mattermost.**
Если карточка была создана БЕЗ текста (`text` пустой/не передан в `POST /api/automation/tasks` — обычный сценарий, когда карточку сначала создают, а текст пишут отдельным вызовом позже) и текст добавлялся позже через `POST .../text` — блок с текстом реально создавался и `caption`/`bytesSaved` в ответе API были корректны, но САМ Mattermost (родной интерфейс Boards, `messager.kontentferma.com`) показывал карточку без текста. Причина — у карточки есть служебное поле `contentOrder` (порядок отображаемых блоков контента), и его выставляет только создание карточки С текстом сразу; более старая версия `POST .../text` создавала блок, но не добавляла его в `contentOrder` — блок существовал, но Mattermost его не показывал.

**Исправлено** — теперь `POST .../text` (и `POST .../keywords`-соседний `POST .../text`, и клиентская правка текста) сам следит за `contentOrder` при каждом сохранении, включая уже сломанные ранее карточки: если текстовый блок не входит в `contentOrder` — он туда добавляется автоматически, без побочных эффектов на остальные поля карточки. **Если у вас уже есть карточки с "потерянным" текстом (как в примере выше) — после деплоя этого фикса просто повторите вызов `POST .../text` для них ещё раз (с тем же или новым текстом) — это самостоятельно почини́т `contentOrder`, вручную в Mattermost ничего делать не нужно.**

**3) Обновить ТОЛЬКО ключевые слова** (текст поста не трогает):
```
POST /api/automation/tasks/bxyz1234567890abcdefghijk/keywords
X-Api-Key: <ваш ключ>
Content-Type: application/json

{ "text": "пляж, отпуск, скидка 25%, UGC-фото" }
```
```json
{ "task": { "id": "bxyz1234567890abcdefghijk", "keywords": "пляж, отпуск, скидка 25%, UGC-фото", ... } }
```

**Ошибки** (обоих update-методов): `400 text_required` (только у `.../text`
— пустой текст поста запрещён; у `.../keywords` пустая строка разрешена,
это способ очистить поле), `502 text_update_failed` /
`502 keywords_update_failed` при сбое записи в Mattermost, `401` без
`X-Api-Key`.

**4) Перевести карточку в «На согласование» после генерации** (или в любой
другой статус — не только 5 клиентских):
```
POST /api/automation/tasks/bxyz1234567890abcdefghijk/status
X-Api-Key: <ваш ключ>
Content-Type: application/json

{ "status": "На согласование" }
```
```json
{ "task": { "id": "bxyz1234567890abcdefghijk", "status": "waiting", "statusLabel": "На согласование", ... } }
```
`status` — точный текст опции свойства «Статус» в Mattermost (регистр и
пробелы по краям не важны, но само слово должно совпадать). Это ОТДЕЛЬНЫЙ
метод от `POST .../publish` ниже — `publish` умеет переводить только в
одну сторону, в «ОПУБЛИКОВАНО» (плюс обязательно записывает ссылку на
пост); `.../status` — это общий метод для любого ДРУГОГО перехода, включая
внутренние стадии («В процессе» и т.п.), которых клиент не видит.

**Ошибки**: `400 status_required` (пустой `status`), `502 status_update_failed`
(опция с таким текстом не найдена в свойстве «Статус» на борде — сообщение
ошибки перечисляет все реально существующие опции; либо сбой записи в
Mattermost), `401` без `X-Api-Key`.

**5) Написать клиенту прямо в чат** (НЕ внутренний аудит-комментарий — это
реально видно клиенту в его кабинете согласования):
```
POST /api/automation/tasks/bxyz1234567890abcdefghijk/client-message
X-Api-Key: <ваш ключ>
Content-Type: application/json

{ "text": "Добавили новую версию текста с учётом ваших пожеланий — посмотрите, пожалуйста!" }
```
```json
{ "task": { "id": "bxyz1234567890abcdefghijk", "clientComments": [ { "kind": "agency", "text": "Добавили новую версию текста...", "createdAt": 1772140800000 }, ... ], ... } }
```
Можно отправить и только картинку (без текста) — `{ "imageUrl": "https://disk.kontentferma.com/s/..." }`, нужна ссылка disk.kontentferma (та же, что и в `media`/`media-link`). Хотя бы одно из полей `text`/`imageUrl` обязательно.

**Ошибки**: `400 text_required` (оба поля пустые), `502 client_message_failed`
(сбой записи в Mattermost), `401` без `X-Api-Key`.

## 6. Telegram-бот «Кот Василий» — регистрация чатов + переписка (отдельный API-ключ)

Это ДРУГАЯ интеграция, не связанная с публикацией SMM-контента выше — свой
собственный n8n-workflow (Telegram Trigger на боте «Кот Василий»), свой
собственный секрет. **Не используйте `AUTOMATION_API_KEY` / `X-Api-Key` для
этих запросов** — нужен отдельный `BOT_API_KEY`, заданный в Dokploy, и
заголовок `X-Bot-Key`. Разделены специально, чтобы этот ключ можно было
ротировать/отозвать независимо от публикационного потока.

**Важно про телефон**: Telegram Bot API НИКОГДА не отдаёт номер телефона
обычного пользователя — ни в `my_chat_member.from`, ни в `message.from`. Там
есть только `id`, `username` (может отсутствовать), `first_name`,
`last_name`. Поля под телефон в этой системе нет — не пытайтесь его туда
писать, взять неоткуда (кроме отдельного экшена «поделиться контактом»,
который в этом флоу не задействован).

Это приложение **не хранит токен бота** и не отправляет сообщения в
Telegram само — только копит очередь исходящих (см. п. 6.3). Реальную
отправку/приём всегда делает n8n через свой Telegram-credential.

### 6.1 Регистрация чата — `POST /api/bot/channels`

Вызывать на КАЖДЫЙ апдейт `my_chat_member` от Telegram Trigger (в ноде
включите `my_chat_member` в параметре Updates — по умолчанию он не
слушается, только `message`/`callback_query`). Не только на «добавили» —
на «удалили»/«выгнали» тоже, иначе список во вкладке «Бот» перестанет быть
достоверным.

```
POST /api/bot/channels
X-Bot-Key: <BOT_API_KEY>
Content-Type: application/json

{
  "chatId": "-1001234567890",
  "chatType": "channel",
  "title": "Прайм кота Василия",
  "status": "administrator",
  "actorUserId": "111222333",
  "actorName": "Иван Иванов",
  "actorUsername": "ivan_ivanov"
}
```
Поля `chatId`/`chatType`/`title`/`status` — напрямую из
`my_chat_member.chat.id/.type/.title` и
`my_chat_member.new_chat_member.status`. `actor*` — из `my_chat_member.from`
(кто выполнил действие); эти поля запоминаются только при ПЕРВОМ появлении
чата — повторные события (например, разжаловали из админов) обновят
`title`/`status`, но не перезапишут «кто добавил».

Ответ: `{ "chat": { "chat_id": "...", "status": "administrator", ... } }`.
Ошибки: `400 chat_id_required` / `400 status_required`, `401
invalid_bot_key`, `503 bot_api_disabled` (BOT_API_KEY не задан на сервере).

### 6.2 Входящее сообщение (лид) — `POST /api/bot/messages`

Вызывать на каждое входящее ТЕКСТОВОЕ сообщение из личного чата с ботом
(`message.chat.type === 'private'`). Групповые/канальные сообщения сюда не
шлите — вкладка «Переписка» показывает только личные чаты (потенциальные
лиды), для каналов/групп есть отдельная вкладка «Бот» (п. 6.1).

```
POST /api/bot/messages
X-Bot-Key: <BOT_API_KEY>
Content-Type: application/json

{
  "chatId": "987654321",
  "chatType": "private",
  "chatTitle": "Пётр Петров",
  "telegramMessageId": "42",
  "fromUserId": "987654321",
  "fromName": "Пётр Петров",
  "fromUsername": "petr_petrov",
  "text": "Здравствуйте, а как подключить бота к моему каналу?"
}
```
Если это первый контакт с этим `chatId` — чат автоматически заведётся и во
вкладке «Переписка» (личные чаты не шлют `my_chat_member` на первое
сообщение, только на блокировку/разблокировку, так что без этого вызова
такой лид был бы не виден вообще).

Ответ: `201 { "message": { "id": 1, "chat_id": "...", "direction": "in", ... } }`.
Ошибки: `400 chat_id_required`, `401 invalid_bot_key`.

### 6.3 Очередь исходящих — `GET /api/bot/messages/outgoing` + `POST /api/bot/messages/{id}/ack`

Когда CEO отвечает лиду из `/ceo/bot-leads`, сообщение сразу НЕ уходит —
оно ставится в очередь (`status: "pending"`). Нужен отдельный n8n-workflow
(например, Schedule Trigger раз в 30-60 секунд), который:

1. `GET /api/bot/messages/outgoing?limit=50` — забирает всё ещё не
   отправленное:
   ```json
   { "messages": [ { "id": 7, "chatId": "987654321", "text": "Здравствуйте! Подключить можно так: ...", "createdAt": "2026-08-30T10:05:00.000Z" } ] }
   ```
2. Для каждого элемента — реальный вызов Telegram Bot API `sendMessage`
   (`chat_id: chatId, text`) со своим credential'ом бота.
3. Отчитаться по каждому сообщению — **обязательно**, иначе оно так и
   останется `pending` и будет отдаваться повторно на каждый опрос
   (задвоенная отправка):
   ```
   POST /api/bot/messages/7/ack
   X-Bot-Key: <BOT_API_KEY>
   Content-Type: application/json

   { "status": "sent", "telegramMessageId": "128" }
   ```
   При неудаче — `{ "status": "failed", "error": "Bad Request: chat not found" }`
   (текст ошибки от Telegram, для наглядности в интерфейсе).

`id` в `.../ack` — это ID СТРОКИ из ответа `.../outgoing` (число), а НЕ
`telegram_message_id` — не перепутайте.

Ошибки: `400 status_invalid` (status не `sent`/`failed`), `400 id_invalid`,
`404 message_not_found` (такой pending-строки уже нет — вероятно, уже
подтверждена или id неверный), `401 invalid_bot_key`.

### 6.4 Настройка BOT_API_KEY

Раньше (и всё ещё можно) — задать `BOT_API_KEY` переменной окружения в
Dokploy и передеплоить. Проще — выпустить его прямо во владельческой вкладке
«Управление» (см. **раздел 7** ниже), без Dokploy и без передеплоя вообще. В
любом случае: в n8n заведите отдельный credential «Header Auth» (имя
заголовка `X-Bot-Key`) для Telegram-Trigger-workflow'а Василия — НЕ
переиспользуйте credential от `AUTOMATION_API_KEY`.

## 7. Живое управление ключами (без Dokploy и без редеплоя)

`AUTOMATION_API_KEY`, `BOT_API_KEY`, `GOOGLE_DOCS_API_KEY` (и любой другой
секрет, который агентство заведёт под свою автоматизацию) больше не обязаны
жить только в переменных окружения Dokploy — владелец (CEO) может
завести/сменить/удалить их прямо из интерфейса: `/ceo` → вкладка
«Управление» (`/ceo/api-keys`). Изменение действует **сразу же, на
следующем запросе** — Postgres-таблица `api_keys` авторитетна поверх
env-переменной, никакого передеплоя не требуется (см. `backend/src/
apiKeys.js`).

Что это значит для вас как для разработчика n8n-потоков:
- Если владелец нажал «Выпустить новый» на каком-то ключе — старое значение
  в вашем credential (`X-Api-Key`/`X-Bot-Key`) сразу перестаёт работать
  (`401 invalid_api_key`/`invalid_bot_key`), пока владелец не пришлёт вам
  новое значение (он его видит прямо в этой вкладке).
- Env-переменная в Dokploy (если она вообще задана) остаётся резервным
  значением только до первого раза, когда владелец что-то сделает с этим
  ключом через вкладку «Управление» — после этого в Postgres появляется
  запись, и именно она становится источником истины.
- Ничего в самом запросе/протоколе не меняется — по-прежнему просто
  `X-Api-Key`/`X-Bot-Key` заголовок с текущим значением.

   **«Согласовано НА ПУБЛИКАЦИЮ»**.

3. Сам пост (текст, фото/видео, к какой соцсети относится) живёт в
   Mattermost Boards, не в Postgres — см. ниже, как его читать.
4. Клиент в кабинете может переставить фото/видео местами — итоговый порядок
   нужно брать через API этого приложения, НЕ читая блоки Mattermost
   напрямую, иначе публикация уйдёт в исходном (не выбранном клиентом)

## Что должна делать автоматизация (по пунктам из исходного запроса)

1. Раз в день (сработать по cron) — читать параметры проекта (учётные данные
   для публикации, per network) из Postgres (`project_settings`).
2. Проходить по задачам в Mattermost Boards и находить те, у которых **дата
   публикации = сегодня**.
3. Публиковать пост в нужной соцсети.
4. Записывать в лог, что публикация произведена.

Ниже — конкретно, как это сделать с данными, которые реально есть в системе.

## 1. Подключение к Postgres

Приложение само создаёт (и обновляет пароль при каждом рестарте) отдельную
Postgres-роль специально для этой автоматизации — **не переиспользуйте
основного пользователя приложения** (`POSTGRES_USER`), у него полные права
суперпользователя на этой базе. Роль для n8n имеет только `SELECT` на
`project_settings` и `SELECT`+`INSERT`+`UPDATE` на `publication_log`.

```
Host:     db (если n8n в той же сети Docker/Dokploy) — либо публичный адрес,
          если n8n развёрнут отдельно (тогда в docker-compose.yml нужно
          раскомментировать проброс порта 5432 — см. комментарий там же)
Port:     5432
Database: значение POSTGRES_DB из .env агентства (по умолчанию kfapproval)
User:     значение N8N_DB_USER из .env агентства (по умолчанию n8n)
Password: значение N8N_DB_PASSWORD — спросите у Дмитрия
```

Таблица `project_settings` (создаётся автоматически при старте приложения,
уже существует к моменту, когда вы начнёте работу):

```sql
CREATE TABLE project_settings (
  board_id text NOT NULL,
  project_id text NOT NULL,          -- id опции свойства "Проект" в Mattermost
  link_token text NOT NULL,          -- НЕ нужен для этой автоматизации
  link_token_updated_at timestamptz,
  logo_url text,                     -- НЕ нужен для этой автоматизации
  social_credentials jsonb,          -- {"ig": {...}, "tg": {...}, "vk": {...}, "ok": {...}, "max": {...}}
  start_date text,                   -- отчётная дата проекта (дата старта), "YYYY-MM-DD" или пусто
  posts_per_month text,              -- количество постов в месяц (число строкой) или пусто
publish_time_msk text,             -- время публикации (МСК), "HH:MM" или пусто
  project_manager text,             -- менеджер проекта
  strategy_prompt text,             -- стратегический промт
  planning_prompt text,              -- промт для планирования постов на месяц
  post_prompt text,                  -- промт для постов
  image_prompt text,                 -- промт для генерации картинок
  updated_at timestamptz,
  PRIMARY KEY (board_id, project_id)
);
```

Таблица для лога публикаций (тоже уже создана, пишите в неё напрямую из
n8n через Postgres-ноду):

```sql
CREATE TABLE publication_log (
  id bigserial PRIMARY KEY,
  board_id text NOT NULL,
  project_id text NOT NULL,
  task_id text NOT NULL,             -- id карточки Mattermost
  network text,                      -- 'ig' | 'tg' | 'vk' | 'ok' | 'max'
  status text NOT NULL,              -- 'success' | 'error' — на ваше усмотрение, но эти два минимум
  message text,                      -- текст ошибки, если status='error'; ссылка/детали, если 'success'

```

`board_id` для этого проекта всегда один и тот же (одна общая доска на всех
клиентов) — см. константы ниже.

## 2. Подключение к Mattermost Boards API

Это НЕ обычный REST API Mattermost — это отдельный, официально не
задокументированный API плагина Boards. Подробности (найдено по исходникам
плагина и подтверждено вживую) — в `docs/MATTERMOST_INTEGRATION.md` этого же
репозитория, здесь только выжимка, нужная для публикации:

```
Base URL:        https://messager.kontentferma.com/plugins/focalboard/api/v2
Team id:         4wd5nx3wffbmjg3a9cjjcgi8tw
Board id:        bzszm3hy9e3gi7yy5nio48jitcr   (борд "Задачи SMM-Team")
```

**Аутентификация** — два варианта, см. `docs/MATTERMOST_INTEGRATION.md` §2
для полных деталей:
- Логин/пароль (`POST /api/v4/users/login`) — то, что уже использует это
  приложение и рабочая n8n-интеграция агентства для других задач. Проще
  всего переиспользовать те же учётные данные, что уже настроены в `.env`
  этого приложения (`MATTERMOST_LOGIN_ID`/`MATTERMOST_PASSWORD`) — спросите
  у Дмитрия, либо попросите завести отдельный технический аккаунт, если
  агентство хочет разделять, кто что делает в Mattermost.
- Personal Access Token — не проверялся на запись (PATCH/POST) на этом
  сервере, см. предупреждение в `docs/MATTERMOST_INTEGRATION.md` §2.

Все запросы — `Authorization: Bearer <token>` + `X-Requested-With:
XMLHttpRequest`.

**Получить карточки:**
```
GET {base}/boards/{boardId}/cards?page=0&per_page=200
```
Свойства карточки — прямо в `card.properties[propertyId]`, НЕ в
`card.fields.properties`. Если карточек станет больше 200 — нужна
пагинация (сейчас в этом проекте её тоже нет, см. `docs/MATTERMOST_INTEGRATION.md` §1а).

**Property id'шники, которые понадобятся:**

| Свойство | id | Тип |
|---|---|---|
| Статус | `a9zf59u8x1rf4ywctpcqama7tio` | select |
| Дедлайн (публикация) | `a1zf7ujfxgqkriwt5x8nwz4urcw` | date |
| Проект | `anrzfu84oz7gi6jzr3crjxgffxr` | select |
| URL | `agd9kbpe3q9t3dz63sgqzxzcbda` | url |

**Значения свойства «Статус», которые нужны:**

| Смысл | option id |
|---|---|
| Согласовано (готово к публикации) | `ao3y74zxfkfnk5fntpnhcbwa4fe` |
| Опубликовано (куда переводить после успешной публикации, см. ниже) | `agkictqb1ep3zj4k4orikz4pzko` |

**Формат даты** в свойстве «Дедлайн (публикация)» — может прийти в одном из
трёх видов, см. `docs/MATTERMOST_INTEGRATION.md` §3: JSON-строка
`{"from":epoch_ms}`, «голый» epoch в миллисекундах, или `YYYY-MM-DD`.
Приводите к дате и сравнивайте с сегодняшней (по МСК, как и весь остальной
проект).

**Медиа (фото/видео) карточки, В ПРАВИЛЬНОМ ПОРЯДКЕ** — НЕ читайте блоки
Mattermost напрямую для этого (см. ниже почему), берите готовый список через
API этого же приложения:

```
GET {appBase}/api/boards/{boardId}/tasks?project={projectOptionId}
```

Без авторизации (тот же публичный эндпоинт, что отдаёт кабинет клиенту) —
`appBase` это адрес самого этого приложения (Dokploy), `projectOptionId` —
то же самое значение свойства «Проект», что и `project_id` в
`project_settings`. В ответе, в `tasks[i].media[]`, для каждой карточки
photos/видео уже идут **в том порядке, который выбрал клиент** (или в
дефолтном, если он ничего не переставлял) — по одному объекту на файл:

```json
{ "id": "…", "source": "mattermost" | "disk", "fileId": "…", "shareUrl": "…", "kind": "image" | "video" | "file", "name": "…" }
```

Скачивать байты — тоже через прокси этого приложения, не напрямую:
```
GET {appBase}/api/files/{boardId}/{fileId}        — для source: "mattermost"
GET {appBase}/api/disk-embed?u={encodeURIComponent(shareUrl)}  — для source: "disk"
```
(поддерживают Range, видео тоже скачаются нормально). Так вам не нужно
самим разбирать/скачивать ссылки disk.kontentferma.\* — приложение уже
это делает.

**Почему не читать блоки Mattermost напрямую**: с фичи «клиент может
переставить фото/видео местами» порядок медиа хранится ОТДЕЛЬНО, в Postgres
(`task_media_order`, ключ — `board_id`+`task_id`, значение — JSON-массив id
медиа в нужном порядке; если строки нет — клиент ничего не переставлял,
действует порядок по умолчанию). У этой автоматизации сознательно НЕТ
доступа к этой таблице (роль `n8n` в Postgres — см. п.1 — прав на неё не
имеет) именно чтобы не пришлось повторять здесь логику сборки итогового
порядка (включая то, как для медиа с диска id считается от хеша ссылки, а
не от позиции — деталь, которую легко воспроизвести неточно). Публичный API
приложения уже делает всю эту сборку и отдаёт готовый результат.

Если понадобится напрямую (для отладки, не для публикации) — сырые блоки
всё ещё читаются как раньше: `GET {base}/boards/{boardId}/blocks`, блоки с
`parentId == <id карточки>` и `fields.fileId` — расширение файла зашито
прямо в `fields.fileId` (например `76ttr5js5efdzbrjy7a5qkqrgbw.mp4`).
Подробнее — `docs/MATTERMOST_INTEGRATION.md` §6.

**Текст поста** — читайте его из **описания карточки** (text-блоки с
`parentId == <id карточки>`, тот же запрос `GET .../blocks`, что и для медиа —
объединяйте в порядке `createAt` через двойной перенос строки). Если в
описании есть секции, берите только блок под заголовком вроде `## Для клиента`
и игнорируйте внутренние заметки в других секциях.

**Разметка** — текст пишется в Telegram-маркдауне (`**жирный**`, `*курсив*`,
`` `код` ``, `[текст](url)`). Чтобы задумка дошла до целевой соцсети как есть:
- **Telegram** — отправляйте с `parse_mode=Markdown`: `**...**` станут жирными
  в посте, переносы сохраняются.
- **Остальные сети** (VK/Instagram/OK/MAX) — форматирование своё или никакое:
  конвертируйте/снимайте маркдаун под их синтаксис, но переносы строк
  обязательно сохраняйте.

## 3. Как определить, в какую соцсеть публиковать

Приложение уже определяет это по началу НАЗВАНИЯ карточки (то же правило,
что рисует значок соцсети в кабинете клиента — `frontend/app.js`,
`detectSocial()`). Продублируйте ТОЧНО ТУ ЖЕ логику:

- Берёте `card.title`.
- Проверяете, начинается ли (без учёта регистра) с одного из: `ig`, `tg`,
  `vk`, `ok`, `max` — причём именно как отдельное "слово" в начале (после
  сокращения должна идти НЕ буква/цифра — то есть "Igor" не должно
  считаться за `ig`).
- Если да — дальше может идти необязательный разделитель: пробел, двоеточие
  `:`, тире `-`/`–`/`—` (в любом сочетании) — их тоже нужно "съесть", чтобы
  получить чистый текст названия без сокращения.
- Соответствие: `ig`→Instagram, `tg`→Telegram, `vk`→ВКонтакте, `ok`→
  Одноклассники, `max`→MAX.
- Если ничего не совпало — у карточки нет опознанной сети; агентство ещё не
  проставило сокращение в названии, публикацию для такой карточки лучше
  пропустить и залогировать как ошибку (`status='error'`, `message='сеть не
  определена по названию'`), а не гадать.

Пример на JS (ровно то же регулярное выражение, что в `app.js`):
```js
const m = String(cardTitle).match(/^(ig|tg|vk|ok|max)\b[\s:\-–—]*/i);
const network = m ? m[1].toLowerCase() : null; // 'ig' | 'tg' | 'vk' | 'ok' | 'max' | null
```

## 4. Ежедневный алгоритм

1. **Cron-триггер**, время — на усмотрение агентства (предлагаю утро по
   МСК, например 08:00, чтобы паблиш успевал пройти до начала рабочего дня
   — но это не принципиально, сработает и в любое другое время).
2. `GET {base}/boards/{boardId}/cards?page=0&per_page=200`.
3. Отфильтровать карточки: `properties["a9zf59u8x1rf4ywctpcqama7tio"] ==
   "ao3y74zxfkfnk5fntpnhcbwa4fe"` (Статус = Согласовано) **И** дата в
   `properties["a1zf7ujfxgqkriwt5x8nwz4urcw"]` == сегодня.
4. Для каждой такой карточки:
   a. Определить сеть по названию (см. п. 3). Нет сети → залогировать
      ошибку, пропустить.
   b. **Проверить `publication_log`** — нет ли уже записи `status='success'`
      для этого `task_id` за сегодня (защита от повторной публикации, если
      воркфлоу почему-то запустится дважды за день, или шаг 4e ниже по
      какой-то причине не сработал в прошлый раз). Есть → пропустить.
   c. Прочитать `project_settings` по `(board_id, project_id)` — `project_id`
      это значение `properties["anrzfu84oz7gi6jzr3crjxgffxr"]` карточки —
      взять `social_credentials[network]`. Нет учётных данных для этой сети
      у этого проекта → залогировать ошибку, пропустить (агентство ещё не
      заполнило попап «Редактировать» для этого клиента/сети).
 d. Скачать текст поста (описание карточки — text-блоки, см. раздел «Текст
    поста» выше; если внутри описания есть секции, берите только `Для клиента`) и
   медиа **в правильном порядке** через `GET {appBase}/api/boards/{boardId}/tasks?project={projectOptionId}`
   (см. «Медиа (фото/видео) карточки, В ПРАВИЛЬНОМ ПОРЯДКЕ» в п. 2 — НЕ через
   сырые блоки Mattermost, порядок клиента там не восстановить) —
   опубликовать в нужной сети, используя учётные
   данные из шага (c). Для Telegram — `parse_mode=Markdown`, чтобы
   `**жирный**` стал жирным в посте. Конкретный вызов API каждой соцсети —
   отдельная задача, зависит от того, что у неё за API (в этом
   проекте это не исследовалось).
   e. При успехе — записать `post_url`, вернувшийся от соцсети (если
      API его отдаёт).
   f. **Записать в `publication_log`** — обязательно, при успехе И при
      ошибке (`status='success'`/`'error'`, `message`, `post_url` если
      есть).
5. **Рекомендую (необязательно, но закрывает цикл с уже готовой фичей
   кабинета)**: при успешной публикации — перевести карточку в Mattermost в
   статус «ОПУБЛИКОВАНО» и заполнить свойство «URL» реальной ссылкой на
   пост. У кабинета клиента уже есть отдельная вкладка «Опубликовано»,
   которая покажет это клиенту автоматически, ничего дополнительно
   настраивать не нужно. Как именно делать PATCH — см. п. 5 ниже, там
   реальный найденный баг формата запроса, важно не наступить на те же
   грабли повторно.
   Этот шаг также даёт основную защиту от повторной публикации — на
   следующий день карточка уже не попадёт в выборку по «Статус = Согласовано»
   (шаг 3), она будет «ОПУБЛИКОВАНО». Проверка `publication_log` (шаг 4b) —
   это второй, подстраховочный уровень защиты на случай, если PATCH зачем-то
   не пройдёт.

## 5. Если делаете шаг 5 (перевод карточки в «Опубликовано»)

**ВАЖНО, реальный найденный баг** (подробно — `docs/MATTERMOST_INTEGRATION.md`
§4): PATCH карточки — это НЕ "обнови одно свойство", а "замени весь объект
properties целиком":

```
PATCH {base}/boards/{boardId}/blocks/{cardId}
{
  "updatedFields": {
    "properties": { /* ВСЕ свойства карточки, включая уже существующие — с одним изменённым/добавленным */ }
  }
}
```

То есть сначала нужно взять текущий `card.properties` целиком (из ответа на
`GET .../cards`), скопировать его, и в копии поменять:
- `properties["a9zf59u8x1rf4ywctpcqama7tio"]` (Статус) →
  `"agkictqb1ep3zj4k4orikz4pzko"` (Опубликовано);
- `properties["agd9kbpe3q9t3dz63sgqzxzcbda"]` (URL) → реальная ссылка на
  опубликованный пост.

Если отправить PATCH только с этими двумя полями (без остальных свойств
карточки) — **все остальные свойства карточки будут стёрты**. Это уже один
раз ловили на этом проекте — не повторяйте ту же ошибку.

## Что нужно подтвердить перед стартом (для Дмитрия)

Из вашего исходного запроса взято дословно: чтение параметров из Postgres,
ежедневный проход по задачам на публикацию по дате, публикация в нужную
сеть, запись в лог. Остальное — мои предположения, стоит подтвердить или
поправить:

1. **Фильтр по статусу «Согласовано»** — предполагаю, что публиковать нужно
   ТОЛЬКО согласованные клиентом посты (иначе смысл кабинета согласования
   теряется). Если нужна другая логика — скажите.
2. **Автоматический перевод карточки в «ОПУБЛИКОВАНО» + заполнение URL**
   (п. 4.5 выше) — это моя рекомендация, не было явно в запросе. Без этого
   шага статус карточки в Mattermost и вкладка «Опубликовано» в кабинете
   клиента не обновятся сами — придётся либо делать это руками, либо

5. **Кто публикует посты без определённой сети или без креды в БД** — сейчас

   вмешательства пост просто не уйдёт и повиснет до следующего дня (пока
